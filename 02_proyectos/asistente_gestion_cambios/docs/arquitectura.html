IEC 62304 · 8.2 — Gestión de Cambios

Del prompt único al backend de agentes

Cómo quedó armado el POC que convierte la skill gestion-cambios-iec62304-8-2 (un solo prompt orquestando 5 módulos sobre Jira) en un backend con un agente por módulo, expuesto como API, con GitHub Issues como almacén de estado en lugar del workflow de Jira. El Módulo 1 (Solicitud) ya tiene dos canales de entrada — formulario y chat — que convergen en la misma lógica de negocio.

Componentes y flujo de una request

Dos canales, un mismo destino (Módulo 1)

Los dos puntos de control

core/auth.py

La API key decide el rol — no el body del request

En la skill original (single-prompt sobre Jira) el rol lo decía el usuario en el chat y el modelo confiaba en la respuesta. Acá el header X-Api-Key resuelve a un rol fijo; ese rol nunca puede mentir sobre quién aprueba.

core/state_machine.py

GitHub no valida transiciones — esta tabla sí

Jira traía gratis un workflow configurable que impedía saltar estados. GitHub Issues solo tiene open/closed, así que los 7 estados se modelan como labels estado:* y esta máquina de estados es la única que decide qué transición es legal.

Lectura del diagrama

Flujo feliz — llamada directa entre componentes, con lo que viaja en la etiqueta.
Corte del flujo — un gate rechaza y responde error; el agente y GitHub nunca se tocan.
Límite de proceso — todo lo de adentro es un solo backend FastAPI; afuera, sistemas externos reales (Claude, GitHub).
